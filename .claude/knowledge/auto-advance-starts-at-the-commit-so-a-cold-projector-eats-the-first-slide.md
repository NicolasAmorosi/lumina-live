## Auto-advance starts its clock at the GO LIVE commit, so a projector that is still opening eats the first slide — and the open time is machine load, not code
**Area:** projection (`src/renderer/src/effects/deck-autoplay.ts`, `src/renderer/src/lib/actions/playback.ts`, `src/renderer/src/projection/ProjectionApp.tsx`)
**Trigger:** `decks.spec.ts` «a .pptx with timings advances by itself» fails with `Expected: 1, Received: null`; "the first slide of the hymn didn't show"; or before bisecting anything by projector-open latency.

- `goLiveWithDeck` commits `base` and `setAutoplay("playing")`, and `scheduleDetached` arms slide 1's timer **at that moment** (`deadline = now + advance`). On the first GO LIVE of a session the projector window does not exist yet: `openIfNeeded` resolves once main created it, but React mounts in the new window later. Slide 1's time on the projector is `advance − (mount − commit)`. If the window takes longer than `advance` to mount, its `getSnapshot` returns slide 1 and the `display-content` push for slide 2 lands 1 ms later. The congregation never sees slide 1.
- Measured 2026-10-22 with `[e2e-debug]` logs (commit → `projector mounted`): normally 0.13–0.4 s, but 1–3 s when main is busy right after a conversion (main's event loop lagged 200–800 ms in that window). The test's fixture advances every 2 s, so a slow open misses slide 1, then the deck ends, `end-of-playback.ts` clears to LOGO, and the poll reads `null` from then on. With a real hymn (several seconds per slide) the first slide is just shortened by the open time. A deck with a soundtrack follows the audio clock instead, so this is about detached timers.
- **The open latency follows the machine, not the commit — don't bisect it on one batch per build.** A first pass measured beta.2, `64ab903` and `2a78b6e` fast (0/30 slow) and `86406bf` slow (6/15). That pointed at `gap-px` in `AppShell`. Re-measured minutes later, `divide-x` was the slow one, and the same `main` went 12/12 fast. Per-build batches run one after another pick up whatever else the Mac is doing. Interleave builds, or measure the cause (main's event-loop lag), before blaming a diff.
- **Fixed 2026-10-22**: `projection:open` (`ipc/handlers/projection.ts`) now answers once the new page has mounted — its own `projection:getSnapshot` settles the wait, with a 5 s bound and the window's `closed` as the other two ways out — instead of once the window exists. Every caller already awaited it before committing (`openIfNeeded`), so the commit, and slide 1's timer with it, lands when the projector can paint. `openIfNeeded` is deduped (`openInFlight`): the wait is now long enough for a second GO LIVE to land in it, and a second `projection:open` closes the window that was about to show.
- Measured by delaying `projection.html` 3 s with `session.webRequest.onBeforeRequest` (deterministic, unlike waiting for the machine to be slow): before, slide 1 never appeared and slide 2 lasted 0.74 s; after, slide 1 lasted 1992/2013/2001 ms. That probe is now `decks.spec.ts` «the EN VIVO that opens the projector still gives slide 1 its whole time».
- **That fix stranded the operator when the window closed during the wait (found 2026-10-23).** The window's `closed` broadcasts `projection-closed` (control: `presentationOpen = false`, the «Reopen» toast) and only then settles the wait, so `openIfNeeded` resumed and set `presentationOpen = true` again, which also retired the toast. The control believed in a projector that did not exist, and no GO LIVE ever reopened it (`openIfNeeded` is a no-op while `presentationOpen`). `media.spec.ts` «closing the projector window from outside does not strand the operator» closes it right after `domcontentloaded`, inside the wait: 10/10 failures on the packaged mac build when run alone, `electronApplication.waitForEvent: Timeout 30000ms exceeded while waiting for event "window"`, yet it passed in the full suite (the mount usually won). The same failure on native Linux had been blamed on Xvfb's single screen. Fixed: `projection:open` answers `false` when `closed` settled it, and `openIfNeeded`/`open` only mark the projector open on `true`. **Any `await` that can span an event which resets the state it is about to write has to learn from its answer whether that event happened**: the event and the reply arrive in that order, so writing state after the `await` always wins.
