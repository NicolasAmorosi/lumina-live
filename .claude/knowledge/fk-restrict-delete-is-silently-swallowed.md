## A `RESTRICT` foreign key rejects a delete with `SQLITE_CONSTRAINT_TRIGGER`, not `SQLITE_CONSTRAINT_FOREIGNKEY` — and every `void someAsyncCall()` handler in the renderer swallows the rejection
**Area:** data, ipc, renderer
**Trigger:** a delete/remove IPC call (`library:remove`, or any future handler deleting a row another table references) that "does nothing" for some rows but works for others; before matching on a better-sqlite3 error `.code` for any constraint failure.

- `service_items.media_asset_id` has `onDelete: "restrict"` (`src/main/db/schema.ts`). Deleting a `media_assets` row still referenced by a saved service's item throws — but the extended SQLite error code for that violation is `SQLITE_CONSTRAINT_TRIGGER`, **not** `SQLITE_CONSTRAINT_FOREIGNKEY`. `SQLITE_CONSTRAINT_FOREIGNKEY` only appears for an *immediate* FK check (e.g. inserting a row with a bad reference); SQLite implements the `RESTRICT`/`CASCADE`/`SET NULL` delete actions internally as trigger-equivalents, so their violation surfaces as `SQLITE_CONSTRAINT_TRIGGER`. Verified empirically with a scratch script reproducing the exact schema — matching on `error.message.includes("FOREIGN KEY constraint failed")` is the only code-independent way to catch this class of error reliably.
- Before this fix, `MediaRepo.remove()` (`src/main/db/repositories/media.repo.ts`) let that error propagate as a plain `Error` → `toIpcError` flattens anything that isn't `instanceof IpcError` to `{code: "UNKNOWN"}` → the renderer's `library.store.ts` `remove()` had no try/catch → `media-browser.tsx`'s delete button called `void remove(selectedId)`. The rejection was a discarded unhandled promise: no error, no UI feedback, the row just stayed. This pattern (`void asyncThing()` on a button `onClick`, no catch anywhere in the chain) also exists for `api.library.setLinkedAudio` in `deck-slides.tsx` (`assign()`/`remove()`, lines ~34-45) — not fixed here, same latent trap, lower-severity because failures there (missing/invalid file) are rarer.
- Fix pattern now in place: `MediaRepo.remove()` catches `Database.SqliteError` matching that message and rethrows `new IpcError({code: "MEDIA_ASSET_IN_USE", ...})`; `library.store.ts`'s `remove()` catches that specific code and sets `removeBlocked` state (any other error still rethrows/stays an unhandled rejection, matching existing app-wide convention); `media-browser.tsx` shows a `Callout` with `t("library.removeBlocked")` when set, cleared on the next selection/tab change. **Do not** match SQLite constraint errors by `.code` alone for a `RESTRICT`/action-triggered case — always check the message text too, or match on both known codes.
