## Main cannot tell "a deck under NEGRO/LOGO" from "no deck at all" — only the control window knows what is live
**Area:** projection, ipc, slides
**Trigger:** anything in main that wants to decide something about "what is currently live" — eviction pins, history attribution, refusing an operation on live content — or any new field you are tempted to read off `projectionState.getSnapshot()`.

- The assumption that bit twice on 2026-09-13: that main knows what is on the projector because it holds the last `ProjectionOutput` (`src/main/services/projection-state.ts`). It does not. `selectOutputWithoutUnderlay` (`src/renderer/src/stores/projection.store.ts`) is a *lossy* projection of the store: with a deck as `base`, NEGRO returns `{kind:"black"}` and LOGO returns `{kind:"logo"}` — the `deckAssetId` is simply gone. Worse, `base === null` **also** returns `{kind:"logo"}`, so "a deck is live, covered" and "nothing is live" are byte-identical from main's side. Only `videoUnderlay` survives an overlay, and only because it was added for a different reason (keeping the `<video>` element's decoder session alive).
- **Bug 1 — the eviction pin.** `projection:show` (`src/main/ipc/handlers/projection.ts`) did `pinDecks("projected", [])` for every output that was not a slide, overlays included. Three minutes of NEGRO over a deck, one `evictIfOverCap` pass in between, and the slides are gone when the overlay lifts — re-opening the exact hole `pinDecks` was wired up to close (see [prewarm-lru-grace-and-linked-audio-full-file-read.md](prewarm-lru-grace-and-linked-audio-full-file-read.md), where `pinDeck` was found with zero callers). Fix: `"black"` and `"logo"` no longer release the pin; only an output that genuinely replaces the content does.
- **Bug 2 — where a "don't touch what's live" guard can live.** A forced reconversion deletes the deck row with the same identity (`insertDeck` in `src/main/db/repositories/slides.repo.ts`), so its `worship://deck/<id>/<n>` urls go 404 under the projector. The obvious place for the guard is the `deck:ensure` handler — and it is the wrong one: main would have to invent a `projectedDeckAssetId` of its own, which goes stale exactly when `base` is cleared (that renders as `logo` too), and a false positive there *blocks an operator action during a service*. The guard is in `reconvertDeck` (`src/renderer/src/lib/actions/deck.ts`), which reads `base` directly.
- The rule: **do not add a second source of truth for "what is live" in main.** Either the fact survives inside `ProjectionOutput` for a reason the projection window itself needs (as `videoUnderlay` does), or the decision belongs to the control window. A main-side guard that is right 95% of the time is worse than no guard, because the 5% is a refusal the operator cannot explain or override mid-service.
