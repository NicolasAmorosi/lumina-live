## An optimistic control must hold its own position until a report confirms it, not until the gesture ends
**Area:** renderer
**Trigger:** a control-window widget that commands the projection window (seek, volume, position) and paints a value the projector reports back — it flicks to the old value for an instant after the operator acts

- The belief was that dropping the local drag state on pointer-up is correct because "the seek has been sent". It isn't: on the live panel the command travels control window → main (`projection:mediaCommand`) → projection window, is applied to the `<video>` there, and only comes back as a `projection:reportMediaStatus` report on the next `seeked`/`timeupdate`. For those ~100-300 ms the bar has no local value and re-paints the last *pre-seek* report — the position the operator just left. Reported symptom: "I tap a point on the bar and it twitches back and then jumps to the position ahead".
- Evidence: `MediaScrubber` (`src/renderer/src/components/ui/media-scrubber.tsx`) did `setDragRatio(null)` and then `commit()` in the same handler, while `currentSeconds` comes from `projection.store.mediaStatus` — written only by the projector's own report. The same component in the centre column never flicked, which is what pinned the cause: `seekPreview()` (`src/renderer/src/lib/actions/preview-playback.ts`) writes `usePreviewStore.positionSeconds` synchronously in the same tick, so there is no window in which the store disagrees with the gesture. Same component, same props, different latency — the bug was never in the widget's geometry.
- The fix is to keep the committed value as `pendingSeconds` and paint it until a report lands within `SEEK_CONFIRM_TOLERANCE_SECONDS` (0.75 s ≈ three `timeupdate` reports, so a position already playing past the target still counts as confirmation), with a `SEEK_CONFIRM_TIMEOUT_MS` (1.5 s) fallback so a seek nothing ever confirms — projection window closed, file broken, position clamped — can't leave the bar showing something that never happened. Do **not** fix this by writing an optimistic entry into `projection.store.mediaStatus`: that record is read by the LIVE monitor's drift correction (`LiveVideo` in `output-view.tsx`), `effects/deck-autoplay.ts` and `effects/end-of-playback.ts`, and it must stay exactly "what the projector reported", including its `paused`/`ended` flags. The optimism belongs to the widget, not to the state of the projector.
- Corollary applied at the same time: the readout next to such a control must read the widget's painted position, not the reported one (`onPositionChange` → `MediaTrackRow`'s `scrubSeconds`), or the two halves of one control show different numbers mid-gesture — and the operator can't see which second he is about to jump to before releasing.
