## A background prewarm needs its own LRU treatment, and `resolveLinkedAudio` must never materialize a whole deck file
**Area:** slides, data
**Trigger:** touching `evictIfOverCap`/`insertDeck`'s `lastUsedAt` in `deck-service.ts`, adding a new background/prewarm code path, or touching `linked-audio.ts`'s binary-hint extraction.

- `evictIfOverCap` (`src/main/slides/deck-service.ts`) only considers deck rows older than a 24h grace window. `insertDeck` used to always stamp `lastUsedAt: now`, so a folder of hundreds of decks prewarmed in the background — never actually opened — was **entirely immune to eviction for a full day**, silently growing the cache past `cacheMaxMb` with no error anywhere. Fix: a `background`-priority conversion backdates `lastUsedAt` by 25h at insert time ("converted just in case" ≠ "used"); opening the deck for real calls `touchDeck` and promotes it normally. The same investigation found `pinDeck` already existed but had **zero callers** — the deck currently on the projector was itself eviction-eligible in production until it got wired into `projection:show`.
- `resolveLinkedAudio`'s legacy-binary hint extraction (`src/main/slides/linked-audio.ts`) used to `fs.readFileSync` the **entire** presentation file and convert it to two full-size strings (`utf16le` + `latin1`) just to regex-search for an external audio filename hint of at most 240 characters. For a 40MB `.pps` that's ~120MB of synchronous allocation on the main thread, paid once per deck — fine for one file, a real freeze across hundreds. Deferring *when* this runs (e.g. to background/lazy) only moves the same cost to whatever path finally calls it (`deck:get`/`toDeckDTO`'s `resolve` flag governs that, see `timings-source-vs-auto-advance-flag.md`'s neighbor entries) — it does not remove the cost itself. The actual fix was to bound the *read*: scan in 4MB chunks with a 512-byte overlap (`HINT_SCAN_CHUNK_BYTES`/`HINT_SCAN_OVERLAP_BYTES` in `linked-audio.ts`) instead of loading the whole file, regardless of who calls it or when.
- General lesson: for any "convert N files at once" feature, ask separately (a) does normal LRU/cache-cap logic actually apply to this batch's insertions, and (b) does every per-file step in the path scale with file *size* rather than a fixed cost — moving *when* something runs never fixes the second kind of problem.
